# EXP-0035 — 침입 의심 조건 완화 (최신 사용자 승인)

사용자 결정: 후보 생성 조건이 지나치게 엄격하므로 일부 오탐을 감수하고 침입 의심을 넓게 만든다. 프레임 수·모델·데이터·영역을 바꾸는 작업이 아니다. **이번 지시는 이전 EXP-0034 종료 당시의 후속 실행 금지보다 최신의 명시적 승인이다.**

현재 상태: 새 판정 코드와 로컬 실행 어댑터 작성, 독립 Python 환경에서 합성/관측 결속 테스트 30개 통과, Python 컴파일 확인. **실제 CCTV 관측 JSON·전체 저장소 회귀·렌더링은 이 환경에서 실행하지 않았다. GitHub 반영은 도구 요청 차단으로 미완료**다. 패치의 기준 main은 `e63f7115ae31223954b04b203e000c6259e0323e`이며, 현행 로컬 변경을 보존해 적용한다.

## 바뀌는 판단

기존의 출발 영역 + 접근 + 신뢰 가능한 마지막 방향 + 경계 쪽 이동 + 선 근접 + 가림 위치 **전부 필수** 구조는 새 소실 의심 경로에서 사용하지 않는다.

새 경로:
1. 마지막 실제 관측 직전 3초 중 **문 주변 또는 가림 주석과 겹치는 실제 관측 2개 이상**.
2. 기존의 1초 소실 대기를 지난 실제 프레임이 존재.
3. 위 조건이면 출발 영역·방향·재등장·VLM 판단이 없어도 `침입 의심`을 만든다.

문 주변은 기존 유한선 근접값(0.8 박스 높이, 최소12px)을 재사용하되 **직전3초의 박스 높이 중앙값**으로 계산한다. 가림은 기존 주석과 관측 박스의 기하 겹침이며, 실제 신체가 가려졌다는 정답이 아니다. 두 공간 조건은 AND가 아니라 OR다. 마지막 작은 박스 하나의 위치/방향만으로 앞선 관측을 무효로 만들지 않는다.

출발 영역, 마지막 방향, ±90°, 외형 비교는 보조 정보다. 방향이 없다고 후보를 차단하지 않고, VLM을 새로 호출하지 않는다. 제자리에서 문 근처 검출이 끊긴 경우도 약한 의심으로 잡힐 수 있다. **이것은 의도한 후보 범위 확대의 비용이며 정상임을 확인한 오탐을 결과에서 그대로 보여준다.**

남기는 제외 조건: 분석 구간이 먼저 끝난 경우, 최근 문·가림 관측 자체가 없는 경우, 문 주변 관측 후 실제 같은 쪽 정상 이탈이 이미 관측된 경우. 예측 박스를 실제 관측으로 추가하지 않는다. 정상 이탈 후 다시 문 근처로 돌아온 경우에는 새 소실을 별도로 평가한다. 기존 침입 의심 기록은 이후 돌아왔다는 이유로 지우지 않는다. `침입 확인`은 자동 출력하지 않는다.

## 추가 파일

- `sceneguard/relaxed_suspicion.py`: 기존 EXP-0034 JSON을 복사해 새 소실 의심과 판정 근거를 추가하는 순수 CPU 모듈.
- `sceneguard/exp0035_application.py`: 기존 원본·관측·scene 결속을 재사용하고 실제 관측의 완전한 대응을 확인하는 실행기.
- `tests/test_relaxed_suspicion.py`: 24개 합성 판정/보존 테스트.
- `tests/test_exp0035_application.py`: 6개 실제 관측 형식 결속 테스트. 예측·중복·변조 행 거부.

기존 코드/결과/원본/모델/사용자 영역/가림 주석/ID/chain/원래 경보를 수정하지 않는다. 과거 EXP-0034의 영역·방향 정보는 설명용으로 읽되 새 필수조건으로 다시 추가하지 않는다. 최신 작업 포인터는 이 문서로 연결하고, 이전 보고서 자체를 수정하지 않는다.

## 로컬 Codex 실행

1. 패치를 기존 변경 손실 없이 적용한다. 원래 저장소 전체와 로컬 자료가 있는 환경에서 아래 두 테스트 및 기존 CPU 회귀를 실행한다. 실제 API/형식 불일치가 있으면 동작 오류만 수정하며, 새 사전 검수 문서 제작을 반복해 실행을 미루지 않는다.

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_relaxed_suspicion.py' -v
.venv/bin/python -m unittest discover -s tests -p 'test_exp0035_application.py' -v
```

2. **기존 EXP-0034 JSON + 기존 검출/추적 파일 + 기존 scene**만 읽어 007·030에 새 소실 의심 규칙을 한 번 적용한다. CPU 작업이며 새 CV/VLM/GPU 추론·새 영상·학습·영역 변경·임계값 sweep은 없다.

```bash
.venv/bin/python -m sceneguard.exp0035_application \
  --key 007 --output outputs/exp0035/007-v1.json
.venv/bin/python -m sceneguard.exp0035_application \
  --key 030 --output outputs/exp0035/030-v1.json
```

기본 baseline은 각각 `outputs/exp0034/007-v1.json`, `030-v1.json`이다. 실제 보존 경로가 다르면 `--baseline`에 정확한 파일을 사용한다. 파일이 없으면 결과를 만들어내지 말고 누락 파일을 명시한다.

3. 새 결과는 기존 renderer 입력 구조와 호환하도록 유지했다. 원본/관측/새 상태 영상을 기존 renderer로 다시 생성한다. 영역 전후 비교가 아니라 **같은 영역의 판정 조건 변경 전후 비교**다.

```bash
.venv/bin/python -m sceneguard.exp0034_evidence render \
  --result outputs/exp0035/007-v1.json --output outputs/exp0035/render007-v1
.venv/bin/python -m sceneguard.exp0034_evidence render \
  --result outputs/exp0035/030-v1.json --output outputs/exp0035/render030-v1
```

전체 저장소와 실제 렌더러 연동은 로컬에서 검증해야 한다. 이름에 EXP-0034가 있는 렌더러를 재사용한다고 과거 결과를 덮어쓰지 않는다.

4. 반드시 새 후보가 늘어난 만큼 정상 상황의 오탐도 함께 확인한다.
   - 007 66–74초 및 raw8/raw13의 소실: 기존 판단 불가가 실제로 의심으로 바뀌는가? 바뀌었다면 어떤 기존 관측이 근거인가?
   - 007 52.5–57.5초 정상 접근 **및 직후 소실 대기 시간**: 정상인데 의심으로 올라간 사례가 있는가? 마지막 관측 시각과 경보 시각을 함께 보아 창 밖이라는 이유로 오탐을 숨기지 않는다.
   - 030: 기존 의심은 유지되는가, 새 후보가 같은 사건의 중복 알림인가?
   - 각 새 후보의 원본 관측·의심 시각·사용한 관측 수·사람 검수 결과를 작은 표로 보고한다. 의심 행 수를 사람 수나 정확도로 세지 않는다.
   - 새 의심이 없어도 완화 조건을 임의로 더 바꾸지 말고 `relaxation_audit`에 남은 정확한 차단 사유를 제시한다.

5. 기존 화면에 새 결과를 별도 등록하고 영상 재생까지 확인한다. `침입 의심 / 침입 확인 / 침입 아님 / 판단 불가`만 상태 용어로 사용한다. 변경 전 결과를 함께 열 수 있게 보존한다. 새 후보를 다시 안정 출발 영역/방향/VLM 허가로 거부하는 추가 veto를 넣지 않는다.

6. 코드·테스트·실제 결과 요약을 GitHub에 게시한다. 원본 CCTV·관측 JSON·좌표·scene·크롭·runtime 데이터는 로컬 전용으로 유지한다. 구현/테스트 성공과 실제 성능 개선은 분리해 보고한다.

**이번에는 새 알고리즘 연구가 아니라 더 느슨한 후보 생성 규칙의 실제 적용이다. 불필요한 알림이 늘어나는 것을 허용하되 정확히 기록하고, 알림 증가 자체를 개선 성공으로 포장하지 않는다.**
