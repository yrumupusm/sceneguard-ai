## Findings requiring revision

### R1 — Medium / P2: a refreshed import can display an obsolete review as current

Locations: `webapp/app.py:133`, `webapp/app.py:138`, `webapp/app.py:144`, `orchestration/catalog.py:112`, `orchestration/catalog.py:117`.

The viewer compares current report/metrics bytes with hashes in the current catalog. It does not compare them with the source hashes bound to the review. Re-exporting records refreshes the catalog hashes while retaining the same `review_path`; the historical review itself is not regenerated by the importer. After a source changes and is imported again, both integrity checks can therefore be true while the displayed review refers to the previous source. This undermines the contract that reviewer opinions remain attached to the reviewed report/metrics versions. The frozen seven imports currently match their review hashes; this finding concerns the supported refresh path, not an observed corruption of those records.

**Fixture observation:** created a temporary report containing `new report`, matching current catalog report/metrics hashes, and a review containing `OLD REVIEW` plus the SHA256 of `old report`. Calling `experiment('EXP-0007')` returned `{'report_match': True, 'metrics_match': True}` and rendered `OLD REVIEW` without the re-review warning. No private source was imported.

**Requested correction:** give each immutable review explicit reviewed-report and reviewed-metrics hashes, distinct from current-import hashes; compare the actual displayed source with that binding. Keep an old review visible only with an explicit stale/unverified label. Add a regression for re-imported content with updated catalog hashes and unchanged review. Also read metric bytes once for parsing and hashing: the current separate opens at lines 142–144 can describe different versions during replacement.

### R2 — Medium / P2: startup reports both services started without checking projection survival

Locations: `orchestration/lab.py:81`, `orchestration/lab.py:85`, `orchestration/lab.py:87`, `orchestration/lab.py:92`.

The controller saves each process identity immediately after spawn, but during readiness it checks only the web process. If the projection reader exits after that first observation, a healthy `/api/catalog` still returns `started: ['web', 'projection']`. For example, an adapter import/config/runtime error can occur after the immediate identity read. Initial spawn is not proof that both services are operating. The UI can later show stale/unverified status, but that does not make the startup receipt accurate.

**Fixture observation:** mocked two spawned processes; the web identity remained live and the projection identity was live on its initial observation and absent on the next one. Mocked `/api/catalog` returned 200. `run(config, 'start')` returned both services in `started`; the projection had never been checked again before that return. This was a deterministic control-flow fixture, not a claim that the coordinator's real projection process failed.

**Requested correction:** revalidate both saved process identities before success and require an observation produced by this projection launch (a disconnected receipt is a valid reported state, not connected success). Return an explicit partial-start failure/degraded state if the reader dies, retaining enough ownership information for safe stop. Add a fixture for projection exit after registration and before web readiness. This finding does not allege that stop signals a reused PID.

### R3 — Low / P3: non-regular file validation can block before rejecting a FIFO

Locations: `webapp/app.py:45`, `webapp/app.py:46`, `webapp/app.py:49`, `webapp/app.py:98`.

`safe_open` opens the final component with blocking `O_RDONLY`, then checks `S_ISREG`. A registered path replaced with a FIFO named, for example, `clip.mp4` blocks in `os.open` before the regular-file rejection. This can hang both an artifact request and the experiment detail's availability check. It requires a local misregistered/replaced file; it is not a remote arbitrary-path or symlink escape. The trusted-local configuration assumption limits severity.

**Fixture observation:** created a FIFO in a disposable temporary directory and invoked `safe_open(temp_root, 'fifo.mp4')` in a dedicated fixture subprocess. It remained blocked after one second, rather than rejecting the non-regular file. Only that exact subprocess was killed and reaped, then the temporary directory was removed.

**Requested correction:** use a nonblocking final open followed by the descriptor type check, or another descriptor-based scheme that rejects special files without blocking and retains symlink/race protection. Add a bounded FIFO fixture test. No real media or server was used for this reproduction.
