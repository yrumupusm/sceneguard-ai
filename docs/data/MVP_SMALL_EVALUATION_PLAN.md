# MVP 소규모 평가와 마무리 — 기존 출력 재사용

2026-10-28 사용자 승인. **계획·작업 지시이며 평가 완료 보고가 아니다.** 기준 저장소 `0a341342a15f3ffdb4ef44f58077e13956eb24c6`. 현재 목표는 새 실험 수를 늘리는 것이 아니라, 이미 통합한 MVP가 어떤 장면을 맞히고 놓치는지 확인하고 재현 가능한 결과로 정리하는 것이다.

## 1. 범위

- EXP-0013의 B(전체 화면 Qwen) / C(고정 감시 영역 Qwen) 저장 출력과 원본 영상·기존 주석·사용자 관찰을 재사용한다.
- **새 GPU 추론·가중치 다운로드·모델/프롬프트/ROI/시간창/판정 규칙 변경·재학습은 하지 않는다.** 누락 파일을 메우기 위한 재추론도 자동 실행하지 않는다.
- CPU 기반 결과 추출·평가 스크립트, 필요한 로컬 검수 클립, 원문을 보존하는 출처 정정, 기존 화면 결과 등록과 README/최종 요약 정리만 허용한다.
- 웹 디자인·원시 답변 표시·실행기 기능 확장은 하지 않는다. 기존 complete/조회 흐름을 재사용한다. 실행을 막는 작은 오류 수정은 이유와 영향 범위를 기록한다.
- 기존 Astra max 총괄 1명, Sol high 평가 구현 담당 1명, Astra high 별도 검토를 사용한다. 불필요한 작업자나 큐를 새로 만들지 않는다.
- 완료 또는 사람 확인이 필요한 지점에서 종합 보고한다. 다음 모델 개선은 이 작업의 자동 후속이 아니다.

## 2. 먼저 근거 정리 — 새 정답을 만들지 않는다

[EXP-0013 관찰 출처 정정](EXP-0013-observation-errata.md)을 읽고 후속 manifest·결론에 적용한다.

- 종료까지 집단 전체의 넘기 미완료 관찰은 **031**의 사용자 관찰이다. 030 EOF 행의 인용과 혼동하지 않는다.
- 007의 56.633→56.667초 박스 변화는 첨부 영상에 대한 **ChatGPT 국소 시각 검토**이며 사용자 확정 음성 라벨이 아니다.
- 030 약 90초 넘기, 006 후기 통행 등 이미 제공한 사용자 관찰은 그 범위에서 이용한다. 사용자가 이미 답한 사항을 같은 의미로 다시 질문하지 않는다.
- 사용자 발언, 공식 라벨, AI 시각 초안, AI의 보고서 텍스트 검토, 추정은 구분한다. 공식 이벤트 외 구간을 자동 정상으로 바꾸지 않는다.
- 기존 EXP 보고서·검토 binding을 조용히 덮어쓰지 않는다. 이번 평가 보고서에 정정 링크와 영향을 기록한다. 원문 변경이 꼭 필요할 때만 명시적 정정과 새 검토/binding을 사용한다.

## 3. 평가 단위와 표본을 먼저 고정

### 목표

주평가 질문은 **선택한 짧은 구간의 감시 대상 경계에서 넘기 시도/진행이 실제로 보였는가, 저장된 출력은 그 구간을 후보로 표시했는가**다. 개인 식별, 모든 사람의 완료, 법적 무단침입, 프레임 단위 onset 정확도는 이번 목표가 아니다.

### 표본

- B/C 양쪽 출력이 있는 007·030·013에서 **최대 12개, 약 5초인 서로 겹치지 않는 기존 분석창**을 선택한다. 원칙적으로 영상별 최대4개다. 분석창 ID와 실제 PTS를 이용하고 새 클립을 모델에 입력하지 않는다.
- 모델 정답률이나 후보 유무를 보고 쉬운 예만 고르지 않는다. 기존 공식 구간·과거 관찰·전체 시간 분포에 근거한 선택 규칙을 먼저 기록하고, 예측과 결합하기 전에 목록/해시를 고정한다. 이미 결과를 본 개발 평가임은 명시한다.
- 통행/접근·넘기·접촉/가림 사례가 포함되도록 선택하되 원하는 클래스 비율을 맞추기 위해 미검수 항목을 정답화하지 않는다. ROI 안의 통행 사례가 필요하다.
- 007의 52.5–57.5초, 030 약90초와 EOF는 **별도 실패 진단 목록**으로 둔다. 결과를 보고 선택한 진단 사례를 대표성 있는 표본처럼 주점수에 임의 추가하지 않는다. 주표본과 겹치면 중복 계수하지 않는다.
- 013은 과거 감사 노출이 있는 카메라 그룹의 진단 검증이다. 완전한 맹검/새 장소 성능이라고 부르지 않는다. C4의 B 결과 재사용은 ROI의 추가 성공 표본이 아니다.
- 006·031에는 이번 full-source B/C 쌍이 없으므로 개발 클립의 참고 진단으로만 사용할 수 있다. 새 원본 실행은 하지 않는다.

### 같은 감시 과제로 비교

B/C의 공동 행동 평가 대상은 **C의 고정 ROI가 실제로 포함하는 감시 대상 경계와 그 주변 행동**으로 맞춘다. 원본 전체 시야의 다른 경계나 ROI 밖 사람에게 생긴 출력은 따로 표시한다. B의 클립 전체 설명만으로 어느 경계를 뜻하는지 모르면 대상 일치 미확정으로 남긴다. ROI 밖 사람을 잘라 없앤 뒤 경보가 없다는 사실을 정상 구분 개선으로 계산하지 않는다. C4 full-frame fallback은 분리한다.

## 4. 정답 근거와 사람 확인을 최소화

manifest의 각 항목에 case_id/source_id/camera_group/window_id/start_pts/end_pts, 평가 경계, reference_label, label_status, evidence_source, uncertainty를 기록한다. 공개 manifest에는 원본 절대 경로·미디어·식별 정보를 넣지 않는다.

- reference_label: `climbing_present` / `no_climbing_observed` / `uncertain`.
- label_status: 출처에 맞게 `human_confirmed_for_scope`, `human_observation_partial`, `official_annotation_reference`, `ai_draft`, `needs_human_review` 등으로 구분한다.
- 특정 프레임에서 사람이 넘는다는 명확한 사용자 근거는 그 프레임이 포함된 구간의 **행동 존재** 판단에 활용할 수 있다. 대략 시각만 있고 경계 포함이 모호하면 확정하지 않는다.
- 한 순간에 넘기가 없다는 관찰은 5초 전체 음성의 근거가 아니다. `no_climbing_observed`의 확정에는 선택한 구간 전체와 평가 경계를 확인한 근거가 필요하다.
- 먼저 기존 근거로 가능한 항목을 채운다. 남은 항목 중 최종 판단을 바꿀 **최대 6개 짧은 구간만 한 묶음으로** 사람에게 요청한다. 더 긴 통합 후보가 아니라 개별 5초 창을 질문하며, 앞뒤 맥락은 별도 표시한다.
- 검수 자료에는 먼저 원본과 감시 영역·시각, 질문만 보여 주고 모델 답변은 별도 파일/접힌 기존 보고서에 둔다. 예측에 맞춰 정답을 정하지 않게 한다. 새 라벨링 웹 앱은 만들지 않는다.
- 질문은 `넘기 있음 / 해당 구간에는 없음 / 가려져 판단 불가`의 간단한 형식이다. 최초 답변 묶음을 받기 전에 같은 질문을 반복하거나 프로젝트 전체를 다시 검수시키지 않는다.
- 필요한 답이 없으면 **평가 준비 완료·사람 확인 대기**로 보고한다. AI가 대신 확정하거나 성능 검증까지 완료했다고 하지 않는다. 사용자가 답하면 라벨과 평가만 갱신하며 GPU 실행은 필요 없다.

## 5. 원시 출력 → 비교표의 연결

실행 담당은 기존 로컬 `windows.jsonl`, 창별 `result.json/input.json`, `events.jsonl`을 읽기 전용으로 처리한다. 숨은 재추론·raw 수정·선택지 재작성은 금지한다.

- 각 case를 B/C의 같은 source·시간창에 연결한다. 실제 입력창 범위·관측 PTS·모델 raw/parsed·상태·반환 근거·참조 해시를 대조한다. 저장된 위치를 임의로 추측하지 말고 registry/실제 파일에서 확인한다.
- **병합된 긴 후보 구간이 정답 시점을 덮는다는 이유만으로 hit를 만들지 않는다.** 해당 고정 평가창의 구성 원시 응답을 사용한다. 여러 사람의 한 구간은 clip-level 표본 한 개이지 여러 사건 TP가 아니다.
- 행동 출력, 그 설명이 원본과 맞는지, 완료 주장, 파싱 상태는 별도 열로 둔다. `stepping_over_boundary` 단어만 맞고 설명은 문 열기이면 행동 근거가 부합했다고 하지 않는다.
- 원시 응답을 불변으로 보존하고, 펜스 제거 후 schema parsing과 원문 형식 준수를 구분한다. 정상 분류와 `indeterminate/parse_failed/insufficient_data/미존재 출력`을 구분한다.
- 양성 주장과 판단 불가를 동시에 출력하면 기존 런타임이 후보를 냈다는 사실은 보존한다. 평가에서 유보로 바꿔 오탐을 숨기지 않는다. 의미 모순은 별도 기록한다.
- 비용은 원래 measured scope로만 보고한다. C의 재사용 응답 시간을 새 추론 비용처럼 세거나 B 대비 속도 개선으로 포장하지 않는다.

## 6. 작은 자료에서도 계산 가능한 것부터

사람 근거가 평가 범위를 충족한 항목만 정량 주평가에 넣는다. 미확정·ROI 밖·매칭 실패·재사용은 수와 이유를 따로 제시한다. 표본 수와 양성/음성 분모를 항상 함께 표시한다.

우선 결과는 `확인된 넘기에서 후보 발생 / 확인된 넘기에서 후보 없음 / 확인된 비넘기에서 후보 발생 / 확인된 비넘기에서 후보 없음 / 응답 불가·유보`의 실제 건수다. 단어/후보 명중과 설명 근거의 부합은 다른 열이다.

- 판단 불가·파싱 실패·입력 부족을 TN으로 계산하지 않는다. 양성 사례에서 후보를 내지 못한 경우에는 전체 후보 발견률의 분모에서 제외하지 않는다.
- 필요한 클래스와 라벨이 확보되면 표본 내 후보 precision/발견률 및 출력 가능 비율을 정확한 분모와 함께 산출할 수 있다. 분모0은 null이다. 후보 precision의 미확정 예측 수를 숨기지 않는다.
- 확정 라벨이 부족하면 정량값은 null로 남기고 이미 확인된 근거와 필요한 답을 보여 준다. 공식 라벨 기반 참고 비교가 있으면 사람 확정 평가와 별도 표로 두며 섞지 않는다.
- 부분적으로 고른 짧은 구간으로 시간당 오탐률·연속 서비스 FPR·전체 영상 사건 recall·독립 장소 정확도를 만들지 않는다. 판단 유보만 하는 구성을 높은 성능으로 선정하지 않는다.
- 별도 사람 검토 없이 언어 모델의 점수를 정답으로 쓰지 않는다. 동일 표본의 B/C 차이를 나란히 보여 주고 가장 좋아 보이는 것만 골라 보고하지 않는다.

## 7. 독립 검토는 제한된 원천까지 확인

이번 검토자는 계획·코드와 함께 **비식별화된 창별 결과 근거**를 확인할 수 있다. 이전 EXP-0013의 집계 요약 전용 범위를 그대로 복제하지 않는다. 필요한 공개/검토용 자료는 실행 담당의 로컬 스크립트가 원천에서 추출하고 위치·SHA와 연결한다.

범위: source/window ID, 실제 시간 범위, B/C 상태·선택 항목, 선정/라벨 근거와 상태, 계산식·분모, 입력/출력 해시, 재사용 여부. 개인 정보 없는 설명 문구는 필요한 최소 텍스트로 요약한다. 전체 원시 응답·미디어·인증정보·원본 경로는 게시하지 않는다. 클라우드 에이전트에 CCTV 픽셀 자동 전송 금지는 유지한다.

검토자는 창 매칭, 라벨 출처/범위, 출력 상태, 집계와 분모를 표본에서 끝까지 추적하고 가능하면 짧은 CPU 평가 테스트를 재실행한다. 영상 의미를 보지 못한 부분은 코드/텍스트 검토라고 표시하고 사람이 확인한 것으로 승격하지 않는다. 근거가 없는 원천 검증을 문구 완화만으로 완료 처리하지 않는다.

## 8. 마무리 결과물과 종료

최소 산출물은 버전 있는 평가 manifest/라벨표, 재실행 가능한 CPU 평가 명령, B/C 비교표, 필요한 로컬 짧은 검수 클립, 검토 기록, 한 페이지 최종 요약이다. 평가 코드는 작은 독립 모듈로 두고 기존 추론·웹·큐를 재설계하지 않는다.

새 평가 ID와 원천/라벨 revision을 사용한다. 이미 완료된 EXP의 결과나 review binding을 덮어쓰지 않는다. 사용자 답변 후에는 평가 revision만 새로 남긴다. 전부 제외·분모0·유보·중복창·ROI밖·재사용·파싱 실패·혼합 action에 대한 최소 단위 테스트와 영향 범위 회귀만 수행한다.

총괄은 최종적으로 다음을 분리해 보고한다.
1. 구현/연속 영상 처리/근거 저장: 기존 확인 결과와 이번 검증 범위.
2. 행동 구분: 평가 가능한 표본과 실제 성과·실패·불확실성.
3. 추천: B/C 잠정 유지 또는 둘 다 성능 보류. 임의 통과 기준이나 기존 출력 강제 채택 금지.
4. 실행·재현: 현재 실제 명령/환경/고정 로컬 데이터 제약. 임의 새 CCTV용 범용 CLI라고 쓰지 않는다.
5. 완료 판단: 기능 프로토타입 완성과 행동 성능 충족을 구분. 성능 부족이면 우선 해결할 실패 유형 하나와 근거를 제안하고 멈춘다.
