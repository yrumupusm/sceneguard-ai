# SceneGuard: 제공된 전체 영상의 고정 버전 정확도 검증

사용자 승인: “응 정확도 한번 검증해보자”. 이번 목표는 새 알고리즘이나 시연 클립 추가가 아니라 **제공된 원본 전체의 실제 실행과 정확도 보고**다.
기준 분석 버전: `548ff7098045f9efc5bd2edfd5ce61431a5e210e` (1차 통합 MVP). 새 평가 코드는 판정 규칙을 변경하지 않는다.
준비: `sceneguard/accuracy_evaluation.py`, 합성 단위시험 26개. **전체 원본 추론/정답 변환/실측 점수는 아직 실행 전**이다.

## 1. 전체 목록과 실행 범위를 먼저 확정한다

- 기존 `data/TS_침입`, `data/TL_침입` 및 제공된 원본의 실제 경로를 대조한다. 초기 기록은 MP4/JSON 45쌍이지만 현재 디스크를 다시 확인한다. 45라는 숫자에 맞추어 파일을 빼거나 만들어내지 않는다.
- 기존 `scripts/audit_aihub_intrusion_labels.py`, `docs/data/AIHUB_INTRUSION_SAMPLE_AUDIT.md`, `AIHUB_INTRUSION_USER_REVIEW.md`, `AIHUB_INTRUSION_EVALUATION_PLAN.md`를 활용한다. 옛 스크립트의 표본 10개 상한을 전체 평가 제한으로 그대로 사용하지 않는다.
- 모든 원본을 목록에 한 번씩 기록한다: 파일/해시, 길이, 해상도, native PTS/FPS, label 해시/대응, 카메라·장소·세션 묶음, 과거 사용 여부, 필요한 scene/portal, 검출 캐시 일치 여부, 실행/정답 상태와 사유.
- 출력 비교영상·크롭·동일 원본 사본은 새 독립 영상으로 세지 않는다. 이름이 달라도 동일 SHA이면 중복을 표시한다. `cctv_distribution` 값을 독립 카메라 ID로 그대로 사용하지 않는다.
- **각 원본의 처음부터 끝까지** 실행한다. 정답 이벤트 구간만 잘라서 처리하지 않는다. 논리적인 상태를 초기화하는 임의 분할이나 같은 구간 중복 합산을 하지 않는다. 프레임을 중복 없는 청크로 나누면 관측/사건 상태는 이어져야 한다.
- `complete`, `partial`, `unsupported`, `failed`, `not_run`을 구분한다. 실패나 미지원 영상을 “정상/경보0”으로 바꾸지 않는다. 전체 영상 수·전체 시간·완전 실행 수·처리 시간 비율을 먼저 보고한다.

## 2. 지원 범위와 필요한 계산을 정직하게 다룬다

- 최신 기본 실행기는 `python -m sceneguard.mvp_pipeline`이다. 과거 EXP 판정 파일을 재생하는 것을 새 전체 검증으로 대체하지 않는다.
- 원본·모델·입력 크기·타임스탬프가 맞는 **동일 FCOS 검출 캐시**는 재사용한다. 캐시가 없거나 짧으면 기존 canonical GPU 큐에서 필요한 전체 구간의 같은 검출기를 실행한다. 이번 승인에는 이 검증에 필요한 기존 모델 계산이 포함된다. “캐시가 없다”는 이유로 지원되는 영상을 조용히 제외하지 않는다. 기존 자원/큐/권한 보호는 유지한다.
- C3/C6은 승인된 설정을 쓴다. 다른 카메라를 C3/C6으로 속이지 않는다. 카메라별 문/안팎/경계 설정이 누락되면 **정지 배경에서 한 번 설정**하는 것은 허용한다. 모델 출력이나 정답 시각을 보며 범위·임계값을 맞추지는 않는다. 사람별 학습용 박스 작업은 없다.
- 현재의 C3/C6 제한 또는 30fps 제한 때문에 전체 실행을 할 수 없으면 그 수와 이유를 보고한다. 29.97fps를 30fps라고 표기하거나 프레임을 몰래 버리지 않는다. 설정 등록 등 최소 호환 변경이 필요하면 변경 내역·새 analysis revision을 먼저 고정하고 동일 규칙 보존 회귀를 수행한 뒤 별도 평가로 구분한다. 지원 확장 결과를 수정 전 버전의 성능으로 합치지 않는다.
- 특히 E01_006은 기존 기록에 JSON/실제 프레임 수 불일치가 있다. 정답 변환의 불확실성과 분석기의 FPS 지원 제한은 서로 다른 문제다. native PTS로 처리하며 불일치를 자동 보정하지 않는다.
- 변경이 큰 FPS/카메라 지원 확장이나 새 모델 작업으로 범위를 늘리지 않는다. 현재 지원 가능한 전체 원본 실행을 먼저 끝내고, 나머지는 전체 목록에 미실행으로 명시한다. 이것을 “전체 영상 검증 완료”라고 부르지 않는다.

## 3. 정답은 기존 자료로 만들되 분석 입력과 분리한다

- 공식 JSON의 `metadata.file_name`, `frame_count`와 `annotations.event_frame`을 원본의 실제 디코딩 인덱스/native PTS에 연결한다. `frame / 30`을 모든 영상에 일괄 적용하지 않는다. 정답 caption/event_frame은 분석기, 구역 선택기, 후보 생성기에 전달하지 않는다.
- 0-based/1-based 기준이 확정되면 그 출처를 남긴다. 불명확하면 두 해석의 **공식 라벨 참조 점수**를 별도 표로 내거나 해당 정밀 시각을 미확정으로 분리한다. 모델 결과에 유리한 해석을 선택하지 않는다. 프레임 수가 맞지 않으면 근거 없이 확정 PTS를 만들지 않는다.
- 기본 양성 기준은 공식 침입 구간을 사건 단위로 해석한 참조다. “물리적으로 침입 완료한 사람 수”나 법적 출입 권한을 평가하지 않는다. 시도/종료 미완료·가림 사례는 기존 사용자 검수와 별도 표시한다. 관측 가능한 침입과 완료 여부를 혼동하지 않는다.
- 평가 단위는 **카메라·출입구의 사건**, 사람이 아니다. 동일 시간에 겹치는 사람별 라벨은 결과를 보기 전에 사건 단위로 정리한다. 원래 라벨과 정리 원칙/개수를 보존하고 예측 카드 수에 맞추어 정답을 합치지 않는다.
- 공식 라벨 기준과 사용자 검수 기준은 `official_reference` / `reviewed`로 나눠 보고한다. 불일치를 조용히 덮어쓰지 않는다. 이미 받은 사용자 관찰은 재사용한다.
- 라벨 밖 전부를 정상으로 만들지 않는다. 공식 주석이 모든 침입을 빠짐없이 담았는지 확인되지 않으면 라벨 밖은 미검수다. 정상 통행/대기 정답은 이미 검수한 시간 마스크와 필요한 추가 원본 검수로 확보한다.
- 새로 애매한 장면은 관련 짧은 클립을 모아 한 번에 요청한다. 정밀 동일인 질문·모든 프레임 사람 박스·반복 검수를 요구하지 않는다. 미확정이 있다고 나머지 실행을 멈추지 않는다. 미확정은 분모/분자와 구분해 남긴다.
- 과거 설계·튜닝에 사용한 007/030 및 초기 10개 감사 영상은 개발자료다. 나머지도 이전 배치/미리보기 이력을 조사한다. 같은 카메라의 추가 영상과 미사용 카메라는 분리한다. 출처가 불명확한 자료를 blind test로 부르지 않는다.

## 4. 두 종류의 점수를 함께 낸다

### A. 사건을 실제 근거로 포착했는가

의심과 자동 확인을 별도 집계한다. 카드 전체가 열려 있던 시간을 양성으로 채우지 않는다.

- 의심: 그 사건에 속한 **새 원래 후보의 decision PTS**만 사용한다.
- 확인: 개별 근거의 **실제 첫 자동 확인 PTS**만 사용한다. 카드가 확인됐다는 이유로 나머지 미결 근거나 과거 시각에 확인 시점을 만들지 않는다.
- 정답 구간 안의 실제 근거와 같은 gate로 일대일 최대 매칭한다. 한 카드가 정답 여러 건을 모두 맞힌 것으로 세지 않고, 한 정답에 반복 카드가 붙으면 나머지는 중복 오경보로 기록한다.
- 이번 scorer는 원본 PTS 반개구간 `[start,end)`와 추가 시간 허용폭 0초를 사용한다. 뒤늦은 탐지는 FP/FN과 지연 사례로 따로 보인다. 유리한 허용폭을 사후 탐색하지 않는다.
- TP/FP/FN, 정밀도, 재현율, F1을 **분자/분모와 함께** 낸다. 미검수 예측이 있으면 headline precision/F1은 null로 남기고 평가 가능 부분의 점수와 보수/낙관 범위를 제시한다. 정확도 숫자를 억지로 하나 만들지 않는다.

### B. 사용자에게 실제로 언제 불필요하게 울렸는가

- 사건별 첫 의심/첫 확인 **알림 의도 PTS**를 각각 평가한다. 뒤에 실제 침입이 생겨 카드가 TP가 되더라도, 앞선 정상 대기에서 울린 알림은 별도의 정상구간 경보로 남긴다.
- 따라서 **사건 검출 정밀도와 첫 경보의 적절성은 서로 다른 표**다. 전자만 좋아도 “오경보가 없다”고 설명하지 않는다. 처음 너무 일찍 확인해버린 경우 역시 후속 양성으로 덮지 않는다.
- 검수된 정상 시간의 잘못된 의심/확인 알림 수와 그 시간(초/분)을 그대로 제시하고 시간당 환산도 병기한다. 짧은 정상 시간·0 FP를 운영 안전성으로 해석하지 않는다.
- 시작시각이 정밀 검수된 경우에만 첫 유효 근거까지의 탐지 지연을 낸다. 공식 시작과의 차이는 `참조 시작 대비 차이`로 따로 표시하고 실제 행동 지연과 혼동하지 않는다. 의심이 먼저 나온 경우 선행 시간도 보존한다.
- 처리시간/영상길이, 실행 실패, 의심 해제 실사례 유무, 사건 중복·합쳐짐을 별도 표로 낸다. 끝난 관찰이나 처음부터 무경보인 통행을 해제 성공으로 세지 않는다.

## 5. 제공된 집계기와 로컬 어댑터

먼저 시험을 실행한다.

```bash
.venv-cv-batch02/bin/python -m unittest discover -s tests -p test_accuracy_evaluation.py -v
```

현재 실제 실행 산출물과 공식/검수 라벨을 **로컬**에서 아래 형식으로 변환하는 최소 어댑터를 작성한다. 영상 실행기와 점수기의 입력을 분리하고 해시/로그로 결속한다. 어댑터는 과거 EXP 종합 결과에서 시각을 복사하지 않는다.

```json
{
  "schema_version": 1,
  "protocol_id": "MVP-ALL-EVENT-EVIDENCE-v1",
  "analysis_revision": "실제로 분석한 코드 SHA",
  "videos": [{
    "video_id": "합성_형식_예시_실제정답아님",
    "split": "development",
    "duration_seconds": 30.0,
    "processed_seconds": 30.0,
    "execution_status": "complete",
    "truth_basis": "reviewed",
    "unresolved_reference_events": 0,
    "events": [{"id":"g1","gate_id":"gate","start":10.0,"end":20.0,
      "onset_precise":true,"provenance":"합성 예시"}],
    "verified_non_event_intervals": [{"gate_id":"gate","start":0.0,"end":10.0,
      "provenance":"합성 예시"}],
    "predictions": [{"id":"card1","gate_id":"gate",
      "suspicion_evidence_pts":[5.0,12.0],"confirmation_evidence_pts":[13.0],
      "notifications":[{"kind":"suspicion","pts":5.0},{"kind":"confirmation","pts":13.0}]}]
  }]
}
```

이 예시는 사건 포착 TP이면서 정상시간 첫 의심 경보가 1건인 경우다. 실제 검증 자료로 쓰지 않는다.

- `predictions.id`는 실행 결과의 사건 ID, evidence timestamp는 실제 새 후보/확인 근거에서 추출한다. 같은 상태가 표시되는 매 프레임을 새 근거로 넣지 않는다.
- execution status가 complete일 때만 전 구간 검출 지표를 계산한다. partial/unsupported/failed/not_run에는 `reason`을 넣고 처리 시간과 정답 사건 수는 전체 명단에 남긴다. 스코어러는 전체 목록의 정답 중 포착한 비율을 별도 제공해 실행 실패가 좋은 점수 뒤에 숨지 않게 한다.
- `truth_basis=unresolved`는 정밀 사건 목록을 비우고 `unresolved_reference_events`에 원래 알려진 개수를 보존한다. 이를 음성으로 만들지 않는다.
- 하나의 보고서에는 동일 원본을 중복 넣지 않는다. 공식/사용자 참조를 동시에 비교할 경우 두 manifest/report로 분리하며 처리 범위는 한 번만 센다.
- 정답·예측·manifest는 로컬 전용이다. 공개에는 비식별 영상 ID별 집계와 범위/한계만 남긴다.

```bash
.venv-cv-batch02/bin/python -m sceneguard.accuracy_evaluation \
  --manifest outputs/validation/mvp-all-v1/evaluation-manifest.json \
  --output outputs/validation/mvp-all-v1/evaluation-report.json
```

집계기는 추론 실행기가 아니다. 위 명령만 실행하고 전체 영상 검증 완료라고 하지 않는다.

## 6. 실행 순서와 완료물

1. 전체 원본/정답/카메라/지원/과거 사용 명단 작성, 해시 고정.
2. 필요한 최소 설정·변환 어댑터와 시험 준비. 분석 버전/정답 버전/매칭 규칙 동결.
3. 전체 지원 영상 처음부터 끝까지 실제 분석. 필요한 같은 검출기 계산을 기존 큐로 수행. 실패는 파일별로 남기고 나머지는 계속한다.
4. 공식 참조와 기존 검수에 각각 점수화. 새 경보뿐 아니라 **정답 사건에 경보가 없는 구간도** 확인한다. 예측 경보만 검수해 recall을 계산하지 않는다.
5. `docs/MVP_FULL_EVALUATION.md`에 전체 실행 범위, 영상별 결과, 개발/추가/새카메라 구분, 두 단계 검출 점수, 정상시간 경보, 잘못된 확인·놓친 침입·지연·지원 제외를 정리한다. 실측 없는 칸은 null/미검증이며 0이나100%로 채우지 않는다.
6. 기존 웹에 결과 표와 실패/미검수 근거 클립을 연결한다. 모든 원본의 긴 비교 영상을 중복 렌더링하지 말고 문제가 있는 구간 중심으로 만든다. 외부 경보 발송/기존 DB/기본 시연 결과 변경은 하지 않는다.
7. 코드·보고서·비식별 지표를 GitHub에 게시하고 커밋/실제 실행 수/전체 수/분모/한계를 보고한다. 결과를 보고 같은 평가 자료에 맞춰 튜닝하지 않는다. 수정은 다음 버전이며 현재 baseline 점수는 보존한다.

완료 보고 첫 문장은 반드시 전체 목록 N개 중 전구간 성공 M개, 미지원/실패/미실행 수로 시작한다. N 전체가 실행되지 않았다면 평가 범위를 제한해 표현한다. 실행·모델 품질·정답 신뢰도·브라우저 확인을 별도로 보고한다.
