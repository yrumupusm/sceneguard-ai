## A. 오탐 후처리는 기존 의심을 엄격하게 되돌리는 작업이 아니다

기존 EXP-0035 후보 생성/영역/모델/추적 결과·EXP-0036의 3초/최대10초 카드 묶음은 그대로다.

새 감사는 오직 `recent_gate_presence_then_loss` 알림 중, 알림 시각까지 실제 측정으로 **짧은 공백 직후 동일한 쪽·거의 같은 위치에서 한 대상이 계속 관측된다는 근거**가 명확한 경우만 검토 전용 후보로 표시한다. 실제 단일인 정답이 아니므로 ID를 합치거나 '침입 아님'으로 자동 전환하지 않는다. 새/옛 ID가 서로 겹쳐 관측되거나 다른 사람이 겹치거나 후보가 여러 개면 알림을 유지한다.

출발 영역·방향·재등장·VLM이 없어도 EXP-0035 의심은 계속 생성된다. 위 조건은 **의심을 없앨 근거**를 따질 때만 필요하다. 기존 선/양측 경보는 보존하며 재등장이 없는007 raw8/13 소실도 이 감사 때문에 취소하지 않는다. 마지막 대기 중에 확인할 수 없는 미래 프레임으로 경보를 소급해서 지우지 않는다.

설정은 하나만 사용한다: 최대 연결 공백 .25초, 이전 .4초, 이후 최소 .4초/3관측, 실제 관측 간격 .2초, IoU .65, 크기 비율1.5, 겹침 경쟁 .25. 모두 초기 후처리 가설이며 정확도·확률이 아니다. 결과에 맞춘 sweep 없음.

실행:

```bash
.venv/bin/python -m unittest discover -s tests -p test_mvp_finish.py -v
.venv/bin/python -m sceneguard.exp0037_application --key 007 \
  --result outputs/exp0035/007-v1.json --output outputs/exp0037/007-v1
.venv/bin/python -m sceneguard.exp0037_application --key 030 \
  --result outputs/exp0035/030-v1.json --output outputs/exp0037/030-v1
```

실제 결과 파일 이름이 다르면 기존 파일을 찾아 경로만 수정한다. 표에서 수치를 역산해 가짜 JSON을 만들지 않는다. 캐시/원본/관측·scene 해시가 다르면 실행을 멈추고 입력 버전 문제를 해결한다. 보호 JSON을 덮어쓰지 않는다.

각 폴더의 `baseline-cards.json`, `proposed-cards.json`, `continuation-audit.json`, `receipt.json`을 기존 카드 UI에 비교 등록한다. `review_only_alerts`도 펼쳐 볼 수 있어야 한다. 원래 event ID/source pointer/시각은 그대로다. 완전한 원래 입력은 `full_original_alerts`와 기존 파일에 보존한다. 모델/검출/추적/VLM 호출0.

007 52.5~57.5초 정상 접근과 지연 알림56~58초, 007의70~73초 의심, 030의90~94초 의심을 원본과 대조한다. 정상 쪽 알림이 줄더라도 핵심 의심이 줄면 후처리를 채택하지 않는다. **0개를 줄이거나 애매하면 그 결과를 그대로 보고하고 기존 기능으로 마무리한다.** 새 사람이 남아 있다는 사실만으로 사라진 다른 사람의 의심을 삭제하지 않는다.

## B. 영상 파일부터 카드까지 실제 연결

로컬 구현 담당자가 기존 entrypoint/카메라·환경을 조사해 **하나의 실행 명령 또는 기존 화면의 분석 시작 버튼**을 완성한다. 가짜 CLI 예제를 README에 쓰거나, 이전 결과를 재생하면서 새 영상 분석이라고 부르지 않는다.

- 입력: 사용자가 로컬에서 선택한 원본 영상과 **이미 설정된 카메라**. 첫 버전은 C3/C6 지원이면 충분하다. 다른 카메라/30fps 이외 데이터는 지원 범위를 명시하고 조용히 임의 설정/재샘플링하지 않는다.
- 흐름: 기존 pretrained FCOS 캐시 생성/검증 → 기존 ByteTrack gap → 현재 scene으로 접근/소실 분석 → EXP-0035 완화 후보 → 채택된 경우에만 A 후처리 → 기존 사건 카드 → 원본 근거 영상 → 기존 서비스 등록.
- 기존 `run_cv`, `replay_gap_tracking`, `approach_disappearance`, `relaxed_suspicion`, `incident_cards`를 재사용한다. 과거 특정 실험의 하드코딩 경로와 출처 검증은 일반화하되 공식 입력/PTS/SHA 검증을 제거하지 않는다.
- 유효한 같은 원본/구간/모델/설정의 캐시가 있으면 재사용하고 화면에 '저장 결과 사용'을 표시한다. 새 검출 실행은 기존 canonical GPU 큐/활성 Run·Task·Dispatch를 통해서만 한다. 새 큐/서버/모델/가중치 다운로드·학습 없음. GPU가 없으면 캐시 경로까지만 완료하고 원본 새 분석 미검증을 명시한다.
- 경로가 바뀌었다는 이유만으로 카메라나 출입구를 자동 추정하지 않는다. 원본 영상 시각과 재생 시각을 구분하고, 잘라낸 구간/전체 분석을 구별해 표시한다. 완료/오류/진행 상태를 저장한다. 중단 뒤 이미 끝난 단계는 바이트 결속을 확인해 재사용한다.
- 시연용007·030은 개발 영상이다. 가능하면 로컬에서 이미 가진 같은 설정 카메라의 짧은 정상/침입 구간 각1개를 먼저 정해 설정 고정 상태로 확인한다. 없으면 평가 미수행으로 남기고 다운로드/새 데이터 프로젝트로 확대하지 않는다. 영상 의미 라벨은 이전 사용자 확인과 새 시각 초안을 구분한다.

## C. 검토 결과 저장 및 화면 연결

`review_store.ReviewStore`를 기존 서비스에 붙인다. 자동 `card.status`는 수정하지 않고 `review_status`, 작성자, 메모, 수정 시각, 버전을 별도로 표시한다. 선택값은 **침입 의심 / 침입 확인 / 침입 아님 / 판단 불가**다. 무응답·시간 경과·VLM 답변이 수동 확인을 대신하지 않는다.

- 현재 등록된 bundle SHA + session + incident ID를 서버에서 검증한 뒤만 조회·저장한다. 클라이언트가 보내는 임의 경로/미등록 카드를 수락하지 않는다. 기존 same-origin 요청 검사와 JSON 요청 정책을 재사용한다. 메모는 HTML이 아닌 텍스트로 렌더한다.
- 검토 DB는 canonical GPU DB/알림 수신 영수증 DB와 **별도 로컬 파일**로 둔다. `runtime/incident-reviews.sqlite3` 등이 가능하다. Git에 DB/검토 메모/원본 자료를 올리지 않는다.
- `expected_version=0`은 최초 작성이다. 두 사람이 동시에 수정했거나 오래된 화면에서 저장하면 `ReviewConflict`를 HTTP409로 표시하고 최신 내용을 다시 불러온다. 변경 이력은 append-only로 보존한다.
- 자동 카드 갱신·폴링·되감기·새로고침·서비스 재시작 뒤에도 검토 결과와 영상/열린 상세가 유지돼야 한다. 새 분석 bundle에 옛 검토 결과를 자동 복사하지 않는다. 수동 확인 시각은 원본 영상 PTS와 별개로 표시한다.
- 이 도구는 저장 모듈이며 인증 기능이 아니다. 기존 로컬 서버의 접근 제한을 그대로 유지한다. 운영 인증 시스템 추가는 이번 범위 밖이다.
