# SceneGuard MVP 1.0 — 통합·검증·시연 마무리

## 이번 사용자 승인과 종료 목표

사용자는 007·030 EXP-0049 비교 영상을 직접 제공했고, 같은 출입구 상황을 한 사건으로 유지하고 의심→확인→문 주변 관찰 종료로 정리하는 방식을 최종 후보로 선택했다. 최신 요청은 **“좋아. 마무리까지 가보자”**다. 새 침입 알고리즘 실험을 이어가는 것이 아니라 기존 구현을 실제 단일 실행 흐름에 연결하고 제한된 오프라인 MVP를 완성한다. 이전 문서의 “실험 종료/기본 적용 보류/새 추론 없음”은 당시 실험 범위이며 이번 통합 승인 자체를 막지 않는다.

마지막 제공 영상에서 확인한 범위: 030은 92.73초 확인 뒤 97.43초 후속 관측이 같은 사건으로 남는 방식이 자연스럽다. 007은 72.13초 확인 후 74.57초에 **문 주변 관찰**을 종료하지만, 뒤 76~79초 안쪽 사람의 이동이 끝났거나 안전해졌다는 뜻은 아니다. 007 후반 일반 보행은 새 의심 없이 통과했다. 이는 장면 관찰이며 정밀 동일인/인원수/시작 프레임 정답은 아니다. 같은 장면의 의미를 반복 질문하지 않는다.

최종 범위: 고정된 C3/C6·native 30fps·로컬 저장 영상의 비실시간 분석, 자동 의심/확인 및 근거 영상, 사건 단위 알림, 관찰 종료, 기존 수동 검토와 이력. 상용 무인감시·법적 무단침입 판단·완벽한 개인 식별·전 카메라 일반화·실시간 처리를 주장하지 않는다.

## 이번에 준비된 코드와 확인 수준

`sceneguard/mvp_pipeline.py`는 영상 입력 → 기존 `video_cards` 검출 캐시/기존 큐/ByteTrack → 같은 영상의 CPU 특징점 → 기존 방향/문 구역/상태 갱신 → EXP49 활동 기반 사건 → 원본 근거 클립/뷰어 manifest를 한 번의 호출로 연결하는 **통합 후보 실행기**다. 원래 영상/기존 검출을 사용하며 EXP42/45/46/48/49 **실행 결과 파일을 입력으로 요구하지 않는다**. 기존 함수의 EXP 명칭은 내부 구현 호환 태그일 뿐 새로운 입력의 결과를 과거 실험으로 위장하지 않는다. 현재 실행의 run/source/hash와 `computed_in_current_run`을 명시한다.

ChatGPT 작업 환경에서 문법 검사와 `test_mvp_pipeline.py` **41개 연결·입출력·모의 백엔드 시험**이 통과했다. 이 환경에는 원래 전체 저장소와 사용자 로컬 캐시/좌표가 없어 실제 RuleBackend 통합/CCTV 실행/브라우저는 미수행이다. 특히 기존 함수 간 실제 스키마·성능은 로컬에서 확인해야 한다. CPU 이미지 추적 시험도 작은 가짜 디코더/엔진을 쓴 연결 시험이며 실제 CCTV 추적 성능 시험이 아니다.

입력 모드와 완료 수준을 구분한다. 기존 캐시로 현재 규칙을 계산하는 것은 “저장 검출 기반 새 분석”이지 과거 판정 재생이 아니다. 같은 요청의 완료 stage만 재사용한다. `analysis_complete`는 화면 등록 완료나 MVP 배포 완료가 아니다. `viewer-manifest.json`의 `registration_status=adapter_required`를 실제 등록 전 완료로 바꾸지 않는다.

## 1. 실제 실행기로 연결 확인

로컬 변경을 보존하고 최신 main을 반영한다. 기존 Run/환경/큐/서버/DB를 재사용한다. 모듈 import와 현재 실제 함수 계약을 먼저 대조하고, 아래 의미를 유지하는 통합 오류는 이번 범위에서 바로 수정·검증한다. 단 한 번의 import/등록 실패로 작업을 종료하거나 새 승인을 기다리지 않는다. 실패/수정 근거를 간단히 남기되 무관한 파일 수만 개를 재감사하지 않는다.

- 원래 `video_cards.execute`는 소스·FCOS cache·ByteTrack·초기 후보만 담당한다. 새 경로는 그 결과에서 같은 실행의 자동 확인·후속 관찰·사건 관리를 만든다. 화면에 예전 카드가 기본 결과로 남지 않게 한다.
- 007은 사용자가 수정한 inside scene, 030은 기존 scene, 두 문 주변 polygon은 최종 사용자 수정본을 사용한다. 실제 경로는 EXP46 저장 request/portal-region에서 찾아 **설정으로** 넘긴다. 좌표를 이 문서에서 추측하거나 안쪽 전체로 대체하지 않는다.
- 이미지 특징을 추출할 때는 기존 seed 설정을 사용하고 EXP42/43의 위쪽 움직임/변형 점수와 새 action 후보는 사용하지 않는다. `collect_paths`는 그 event/signals를 버린다.
- 합성·계약 시험 후 실제 RuleBackend로 007/030 저장 검출과 원본을 처리한다. 새 CPU 특징 경로 계산은 통합에 필요한 동일 알고리즘 재계산이다. 무조건 “flow 호출0”으로 보고하지 않는다.
- 새로운 검출 캐시가 필요한 평가 구간은 기존 canonical GPU 큐·자원 기준으로 기존 FCOS만 사용한다. 새 모델/학습/가중치 탐색/수동 사람 박스/VLM 판정 추가는 없다. 007/030 시각·ID를 알고리즘 예외로 넣지 않는다.
- 경보 0개의 정상 영상도 성공한 분석이다. 의심이 하나도 없는 입력이나 새 portal 의심만 있는 입력에서 더미 이벤트를 만들거나 역사적 후보를 복사하지 않는다.

예시(실제 `PORTAL_C3` 경로는 기존 로컬 기록에서 해석):

```bash
.venv-cv-batch02/bin/python -m sceneguard.mvp_pipeline \
  --video data/TS_침입/E01_007.mp4 --camera C3 \
  --scene runtime/region-revisions/007-inside-20261101-v1/scene007.json \
  --portal "$PORTAL_C3" --cache outputs/exp0029/cache007 \
  --start 48 --end 105 --output outputs/mvp-v1/007-acceptance
```

030도 같은 명령의 카메라·실제 scene/portal/cache/video만 바꾼다. 이전 request를 바꿔 resume하지 말고 새 출력 경로를 사용한다. 기존 결과 파일은 회귀 **비교 기준**으로만 읽고 새 분석의 입력/정답으로 끼워 넣지 않는다.

## 2. 화면 등록과 기본 시연 연결 — 구현까지 완료할 것

새 manifest의 `kind=sceneguard_mvp_viewer_v1`, bundle `contract=gate_activity_episodes_v1`, `experiment=MVP-0002`를 기존 서비스에 받는 최소 어댑터/등록 옵션을 구현한다. 아직 이 연결은 제공 코드에 없다. 기존 EXP49 어댑터의 시간순 card/evidence/prefix 표시를 재사용하되 현재 run 출처와 정답 검증 상태를 정확하게 표시한다. experiment 허용 목록/API 등록/실제 목록 노출을 함께 확인한다. `--register-config`와 명시적인 `--registration-id` 또는 같은 기능의 기존 안전한 등록 명령을 통합 CLI에 연결한다.

기본 보기는 **SceneGuard / 영상 분석 / 진행 중 사건 / 종료 이력 / 근거 보기 / 수동 검토**다. 사용자가 EXP49를 찾아야만 최신 기능을 볼 수 있게 두지 않는다. 예전 실험은 별도 비교 이력으로 유지한다. 일반 화면에서 run ID·pending 개수·시험 수·원시 계보는 상세로 접는다. 사람 수처럼 표시하지 않는다. 필수 문구:

- `침입 의심`, `침입 확인 · 자동`, `의심 해제`
- `문 주변 관찰 중`, `문 주변 관찰 종료` — 종료≠해제≠현장 안전
- 분석 방식 `저장 검출 기반 분석` / `기존 모델 새 검출 분석` / `완료 결과 재생`
- 수동 검토는 별도 기록. 자동 상태로 수동 메모/이력을 덮어쓰지 않는다.

사건별 첫 의심/첫 확인을 구분하고 확인 후 후속 관측은 같은 사건에 추가한다. 알림 키 안정성/새로고침/재시작을 검사한다. 테스트 외부 알림을 임의 발송하거나 영수증/DB를 초기화하지 않는다.

## 3. 최종 검증 — 새 알고리즘 탐색으로 확대하지 않음

먼저 007/030에서 채택한 동작의 회귀를 확인한다. 통합 과정에서 세션 ID는 달라질 수 있으므로 ID 문자열 자체보다 원본 시각·후보 참조·자동 상태·첫 확인·종료 및 알림 횟수를 대조한다. CPU 경로가 달라지면 입력/seed/구역 계약부터 진단하고 결과를 과거 파일에서 복사하지 않는다.

| 실제 확인 | 마무리 기준 |
|---|---|
|007 개발 구간|같은 사건에서 의심→확인, 확인 이력 보존 후 관찰 종료, 후반 일반 보행에 새 경보/재개 없음|
|030 개발 구간|하나의 확인 사건에 후속 관측 추가, 같은 확인 반복 경보와 뒤늦은 별도 미결 카드 없음|
|정상/빈 결과|실제 정상 보유 구간에서 0경보 허용, 빈 목록/영상·완료 표시 정상|
|새 입력 경로|가능하면 기존 규칙 조정에 쓰지 않은 같은 카메라의 보유 구간 하나를 고정 설정으로 분석. 파일명/시각 예외 없음|
|바깥 이탈 해제|보유 영상에 문 접근→실제 바깥 이탈이 있으면 확인. 없으면 **실제 해제 미검증**으로 남김. 일반 통행 무경보와 관찰 종료를 해제 성공으로 세지 않음|
|재실행/장애|같은 요청 재실행 시 모델/CPU 경로의 불필요한 재계산 없음, source 변경은 재사용 거부, 오류/차단을 완료로 표시하지 않음|
|사용자 화면|기본 결과 선택, 근거 seek/되감기/상태/관찰 종료/폴링/새로고침/재시작·검토 유지 실제 확인|

새 영상/해제 사례를 확보하지 못하더라도 미검증으로 명시하고 **제한된 고정 카메라 오프라인 시연 MVP**를 마무리할 수 있다. 그 한계를 해소하려고 끝없이 실험을 추가하거나 사용자에게 새 학습 데이터를 만들라고 요구하지 않는다. 실제 상태를 잘못 취소하거나 기본 실행이 실패하면 통합 완료로 보고하지 않고 해당 결함만 수정한다. 새로운 애매한 장면만 짧은 원본을 요청하며 이미 본 007/030 장면은 반복 질문하지 않는다.

## 4. 문서·시연·최종 완료 보고

`docs/MVP_V1_GUIDE.md`를 실제로 성공한 환경·scene/portal 선택·등록 명령에 맞춰 완성하고 root README를 최신 기본 흐름으로 갱신한다. 현재 문서는 실행기 준비 단계이므로 사용자가 명령을 그대로 실행할 수 있도록 최종 확정 경로/설정 찾는 법을 기록한다. Git에는 실제 CCTV/좌표/모델/캐시/수동 메모/DB/인증정보를 넣지 않는다. 기존 README와 실험 기록은 이력으로 보존한다.

실제 완료 보고 `docs/MVP_V1_RELEASE.md`는 다음만 간결하게 담는다: 완료 커밋, 단일 실행/실제 화면 진입, 사용한 영상 범위, 사건/알림/첫 확인/종료, 새 입력 검증 유무, 실제 해제 검증 유무, 캐시/새 추론/재생 구분, 남은 한계, 운영 기본 연결/되돌리기 방법. 시험 수를 정확도로 제시하거나 알려진 두 영상에서 나온 상태를 일반화하지 않는다.

이번 사용자 승인은 **회귀·화면 확인 뒤 최신 경로를 제한된 MVP의 기본 시연으로 연결하는 것까지** 포함한다. 검사할수록 항상 “기본 적용 보류”만 되풀이하지 않는다. 기존 기본 기능을 삭제하지 말고 명시적인 이전 보기로 되돌릴 수 있게 한다. 조건을 만족하면 `MVP 1차 완료 — 고정 카메라·비실시간·자동 해제 실검증 제한`처럼 완료 범위와 한계를 함께 보고한다. 코드 준비/합성 시험/API 등록만 된 상태는 전체 마무리 완료가 아니다.
