# EXP-0042 — 보이는 동안의 변화로 침입 의심 생성

2026-11-01 최신 사용자 승인. 목표는 **대기에서 침입을 의심할 변화가 생기는 구간을 포착**하는 것이다. 이전 실험의 종료 문구는 당시 범위이고 이번 명시적 승인을 막지 않는다. ‘계속 보이면 알림 제외’ 방식, EXP-0041의 0.55/0.65 제외 정책은 사용하지 않는다.

## 구현된 범위 / 실행 전 범위

- `sceneguard/gate_transition.py`: 실제 원본의 짧은 영상 특징 경로와 경계 주변 변화를 계산하는 CPU 경로. 후보 생성에 ID 소실/같은 ID/반대편 재등장/VLM 동의를 요구하지 않는다.
- `sceneguard/exp0042_application.py`: 기존 원본·저장 검출·카메라 설정을 읽어 **선택 구간 전체를 순서대로** 분석한다. 이전 14개 소실 끝점만 평가하는 것이 아니다.
- 작성 환경에서 **46개 시험 통과**: 원본 대신 합성 영상/좌표로 핵심38개, 분할·정규화 계약8개. 계약8개의 묶음 의존성은 주입된 모의 함수다. 실제 기존 묶음 모듈·CCTV·전체 회귀·웹은 로컬에서 확인해야 한다. 실제 CCTV 성능은 아직 미측정.
- 초기 합성 시험에서 부분 움직임이 중앙값에 묻히는 문제와 검출 소실 후 대상 특징이 배경 추정에 섞이는 문제를 발견해 수정했다. 성공한 최종 시험만 CCTV 성능으로 확대하지 않는다.

## 바꾼 판단과 한계

1. 기존 사람 검출 근처에서 영상 특징을 자동 추출한다. 겹친 박스의 픽셀을 전부 지우지 않는다. 실제 검출이 있으면 미확정 ID도 시작점으로 쓸 수 있다. 예측 박스는 제외한다.
2. 짧은 영상 경로는 ID 변화나 검출 누락이 있어도 원본 픽셀을 따라간다. 영상 전체를 재식별하거나 raw ID를 합치는 것은 아니다. 점별 전후방 LK 검사는 유지한다.
3. 기존 선의 **유한 구간을 가로지르는 특징 이동**, 또는 **경계 근처에서 위쪽 움직임과 국소적인 변화가 함께 나타나는 경우**를 새 후보 근거로 평가한다. 일반적인 접근/일괄 평행이동/박스 크기 변화만으로 두 번째 경로가 켜지지 않게 했다.
4. 위쪽 이동은 화면 좌표의 신호일 뿐 신체 부위·구체 행동 이름이나 실제 높이를 인식하는 기능이 아니다. 선을 넘는 픽셀도 사람의 실제 침입 정답이 아니다. 일반 보행·물건 취급·배경 특징 때문에 오탐할 수 있으므로 원본으로 확인한다.
5. 대기하던 구간에 후보가 없었어도 이후 프레임을 계속 평가한다. 관측 연속성을 정상 판정이나 경보 취소로 쓰지 않는다. 특징을 놓치면 새 후보를 만들지 않을 뿐, 기존 소실 의심을 삭제하지 않는다.
6. 기준은 초기 휴리스틱이다. 기본 새 변화 점수0.55는 **폐기한 연속성 제외 점수0.55와 전혀 다른 값**이다. 확률이 아니다. 최근0.35초 내 최소3회/0.10초의 근거를 모으되 중간 프레임 하나 미달을 전체 실패로 보지 않는다. 1초 후보 cooldown과 기존3초/10초 사건 묶음은 별개다.
7. 기존 C3/C6 양방향 설정만 지원한다. 카메라 보정은 배경 특징의 일관된 이동을 참고하며 불확실하면 기록·감점한다. 이것으로 모든 카메라 흔들림을 해결했다고 하지 않는다. 기본 최대16개 짧은 경로/각48점을 사용하므로 자원 한계와 부분 관측도 기록한다.

## 로컬 실행

로컬 변경을 보존해 최신 main을 반영하고 기존 CV 환경을 쓴다. 새 설치·GPU·검출기/ByteTrack 재실행·VLM·학습·데이터 수집·수동 박스·영역 수정은 없다. **CPU 원본 영상 특징 계산은 새로 수행**한다. 원본은 모델 서비스로 보내지 않는다.

```bash
.venv-cv-batch02/bin/python -m unittest discover -s tests -p 'test_gate_transition.py' -v
.venv-cv-batch02/bin/python -m unittest discover -s tests -p 'test_exp0042_contract.py' -v
.venv-cv-batch02/bin/python -m sceneguard.exp0042_application \
  --baseline outputs/exp0035/007-v1.json --output outputs/exp0042/007-v1
.venv-cv-batch02/bin/python -m sceneguard.exp0042_application \
  --baseline outputs/exp0035/030-v1.json --output outputs/exp0042/030-v1
```

실행기와 기존 `validated_inputs`/native decoder/`group_notifications` 통합을 먼저 확인한다. 경로·형식·실행 오류는 수정하고 실패 기록을 보존한다. 원본이나 오래된 결과를 덮어쓰지 않는다. 결과를 본 뒤 특정65초/ID7 같은 예외를 넣거나 장면마다 설정을 따로 맞추지 않는다.

## 결과를 반드시 세 가지로 구분

- `baseline-cards.json`: 원래 후보와 경보.
- `transition-only-cards.json`: **새 후보 생성기의 독립 진단**. 기존 소실 fallback을 빠뜨리므로 최종 제품으로 표시하지 않는다.
- `combined-cards.json`: 기존 후보 전부 + 새 변화 후보. 기존 의심 삭제0. **이 보기에선 기존 오탐을 줄였다고 주장할 수 없다.**

`frame-evidence.jsonl`은 매 프레임의 점수·성분·점 경로·시작/참조/현재PTS를 담는다. `transition-events.json`은 새 후보만 담는다. 원본 candidate payload/ID는 불변이지만 새 후보 추가로 사건 묶음의 시작·소속이 바뀔 수 있으므로 과거 card ID까지 같다고 강제하지 않는다. 사건 먼저 묶기와 최초 통지 시각 원칙은 유지한다. 새 후보가 기존 카드에 묶여 최초 알림이 변하지 않아도 **새 근거 발생 시각**을 따로 보여준다.

## 의미 있는 검출 확인

00748–105초·03084–100초 전체를 같은 규칙으로 비교한다. 알고리즘에는 정답 시각·영상 이름별 예외를 넣지 않는다. 다음 시각은 **사후 검토용**이다.

- 007의 접근·대기(기존56–63초 근처)에서 새 변화 후보가 계속 잘못 발생하는가?
- 사용자 확인 침입 시작이 포함된65초대 및64–74초 문맥에서, 사람이 보이는 중에도 새 후보를 만드는가? 70.13초까지 기다리던 경로보다 새 근거가 빨라지는가?
- 정확한 시작 프레임은 미지정이고 예전 클립에 후보 뒤0.5초가 포함됐다.65.333초를 정답으로 하드코딩하거나 기존 시작 검수를 다시 요구하지 않는다. 후보 전후 원본 문맥으로 사건 수준의 적절성을 본다.
- 030 접근(86초 근처)과90–94초 침입 문맥에서 같은 규칙의 득실을 비교한다. 기존 의심은 합쳐진 보기에서도 보존한다.

새 후보마다 원본·실제 검출·특징 경로·기존/새 후보 시각을 같이 확인한다. 점이 문/다른 사람을 따라갔는지, 단순 보행이나 카메라 움직임을 침입으로 본 것은 아닌지도 기록한다. 새 후보0이거나 대기 때도 계속 울리면 실제 목표 미달이다. 후보 수 증가·합성 시험 통과·기존 경보 보존만으로 개선이라고 하지 않는다. 필요한 경우 **이전에 보지 않은 새로운 후보의 짧은 구간만** 묶어 사용자에게 보여주며, 수동 박스/완벽한 동일인 검수를 전제하지 않는다.

## 전달과 채택

기존 담당3에 baseline / 새 후보만 / 결합 보기와 원본 비교 자료를 최소 어댑터로 등록한다. 점수는 해당시점에 계산된 값으로 표시하고 미래 최종값을 과거 화면에 그리지 않는다. `notify`를 소비하고 기존 검토DB/통지 영수증을 초기화하지 않는다. 실제 표시·재생/seek·폴링·되감기를 확인하고 결과·독립 코드/수치 검토·전달 기록을 게시한다.

새 후보 생성에 실제 이득이 확인되면 다음에 이 근거로 대기/침입의 경보 정책을 연결한다. 이번 **결합은 기존 오탐을 없애는 완성본이 아니다**. 기본 MVP 자동 교체 없이 실제 신규 포착·오탐·처리 비용을 먼저 제시한다. 새 학습이나 더 큰 VLM으로 자동 확대하지 않는다. 화면의 판단 용어는 침입 의심/침입 확인/침입 아님/판단 불가를 유지하며 자동 침입 확인은 하지 않는다.
